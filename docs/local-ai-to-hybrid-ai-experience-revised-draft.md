# 로컬 AI에서 하이브리드 AI까지: 실제 개발 환경에서 선택의 기준을 만들다

## 1. 문제는 AI를 사용할 수 있느냐가 아니라, 어떻게 지속적으로 활용하느냐였다

AI 코딩 도구가 빠르게 발전하면서 개발 업무에 활용할 수 있는 선택지도 많아졌다. 그러나 실제 업무 환경에서는 모델의 성능이나 기능 목록만으로 도구를 선택하기 어렵다.

외부 서비스에 대한 의존성, 사용 비용, 데이터 처리 조건, 응답 속도, 개발 환경과의 호환성, 생성된 결과를 검증하는 데 필요한 시간까지 고려해야 한다.

나 역시 제한된 업무 환경에서 AI를 활용할 방법을 고민하면서 로컬 AI에 관심을 갖게 되었다. 단순히 새로운 기술을 사용해 보는 것이 목적은 아니었다. 실제 개발에 사용할 수 있는 환경을 구성하고, 그 환경의 가능성과 한계를 확인하는 것이 우선이었다.

이 과정에서 한 가지 방향을 세웠다. 새로운 도구를 계속 추가하기보다 현재 환경에서 해결할 수 있는 문제부터 확인하고, 변경이 필요하다면 실행 결과를 근거로 결정하는 것이다.

## 2. 로컬 추론 환경을 구성하고 실제 연결을 확인하다

기본 환경은 Windows 네이티브 개발 클라이언트와 Ollama 기반 추론 서버로 구성했다. 개발 클라이언트는 Lenovo ThinkPad, 추론 서버는 NVIDIA GeForce RTX 5070 Ti Laptop GPU를 탑재한 HP OMEN MAX 노트북이다. 기록된 주요 모델은 `qwen3:8b`이며, 주력 코딩 에이전트는 Aider다.

서버와 클라이언트를 분리한 구성에서는 모델 자체의 실행 여부뿐 아니라 네트워크를 통한 접근과 API 응답도 확인해야 한다.

2026년 10월 15일에는 ThinkPad에서 OMEN 서버의 Ollama API에 접근하고, 원격 모델 목록과 버전을 조회한 뒤 `qwen3:8b`에 직접 추론 요청을 수행했다. 테스트 요청에서 기대한 문자열인 `LOCAL_AI_INFERENCE_OK`를 받았으며, 해당 요청의 전체 처리 시간은 2,871ms로 기록되었다.

당시 검증 환경은 Visual Studio Code 1.142.0 (x64), Aider 0.86.2 및 Ollama 0.40.4로 구성되어 있었다. 이는 해당 시점의 환경을 기록한 것이며, 이후 버전에서도 동일한 결과가 보장된다는 의미는 아니다.

이 검증을 통해 당시 구성에서 원격 API 접근과 테스트한 모델 추론이 정상 작동한다는 사실을 확인했다.

다만 이 결과를 전체 개발 생산성의 증거로 해석하지는 않았다. 단일 추론 요청은 코드 수정의 정확성, 테스트 실행, 오류 복구, 반복 작업의 안정성까지 입증하지 못한다. 실제 코딩 에이전트의 작업 흐름은 별도의 검증 대상이다.

이처럼 검증의 범위를 명확하게 정하는 것은 기술적 경험을 신뢰할 수 있는 기록으로 만드는 데 중요하다.

## 3. 로컬 AI를 선택했다고 모든 비용과 제약이 사라지는 것은 아니다

로컬 AI는 추론 환경을 직접 관리할 수 있고 외부 AI 서비스에 대한 의존을 줄일 수 있다는 장점이 있다. 반면 모델의 품질과 하드웨어 자원, 설정 및 유지보수 부담을 직접 고려해야 한다.

비용 역시 API 사용료만으로 판단할 수 없다. 로컬 환경에는 하드웨어와 전력, 유지보수 및 장애 해결에 필요한 시간이 들어간다. 클라우드 환경에서는 서비스 이용료와 외부 서비스 의존성, 데이터 처리 조건 등을 검토해야 한다.

보안도 마찬가지다. 로컬에서 추론한다는 사실만으로 모든 데이터가 외부에 노출되지 않는다고 단정할 수는 없다. 네트워크 구성, 외부 API 호출, 로그와 도구 권한 등 실제 데이터 처리 경로를 확인해야 한다.

따라서 로컬 AI가 항상 더 저렴하거나 더 뛰어나다고 주장하기보다, 어떤 조건에서 로컬 실행이 적합하고 어떤 상황에서 다른 선택지가 필요한지 판단하는 것이 중요하다고 보았다.

## 4. 로컬과 클라우드 중 하나를 고르는 대신 작업에 맞는 기준을 세우다

로컬 AI를 사용하면서 관심은 실행 환경 자체에서 작업에 적합한 환경을 선택하는 문제로 옮겨 갔다.

모든 작업을 동일한 모델과 도구로 처리할 필요는 없다. 로컬 모델로 충분히 수행할 수 있는 작업은 기존 환경을 우선 활용하고, 요구되는 정확도나 추론 수준을 충족하기 어려운 작업은 다른 모델이나 서비스를 검토할 수 있다.

다만 이러한 구분은 아직 모든 작업에서 비교 실험으로 확정한 결과가 아니라, 실제 평가에 적용할 의사결정 기준이다. 현재 하이브리드 AI는 완성된 운영 구성을 뜻하지 않는다. 로컬 실행을 기본 출발점으로 삼되, 작업의 요구사항과 검증 결과에 따라 다른 모델이나 서비스를 선택적으로 검토하려는 방향이다.

| 판단 기준 | 검토할 내용 |
|---|---|
| 작업 품질 | 결과가 요구사항을 충족하며 테스트로 확인 가능한가? |
| 데이터 보호 | 해당 정보를 외부 서비스로 전송할 수 있는가? |
| 총비용 | 이용료뿐 아니라 유지보수와 수동 수정 시간까지 고려했는가? |
| 응답 시간 | 실제 개발 흐름에서 지연이 허용 가능한가? |
| 운영 부담 | 설정과 장애 대응에 드는 노력이 얻는 이익에 비해 합리적인가? |

이 기준을 바탕으로 로컬 실행을 기본 출발점으로 삼되, 필요에 따라 다른 실행 환경을 검토하는 하이브리드 AI 방향을 생각하고 있다.

중요한 것은 하이브리드 구성을 도입하는 행위 자체가 아니다. 실제 문제를 해결하는 데 도움이 되는지 확인한 뒤 구성 요소를 추가하는 것이다.

## 5. 코딩 에이전트도 실제 작업으로 평가해야 한다

모델의 성능만큼 중요한 것이 모델을 개발 작업에 연결하는 코딩 에이전트다.

2026년 10월 15일 당시 Aider를 주력 코딩 에이전트로 유지하고 있었다. CECLI는 Aider 대체 후보였으며, 실제 코드 수정과 테스트를 포함한 작업 흐름에서 대체 가능성을 평가하는 것은 향후 과제로 남겨 두었다. OpenCode는 보조 후보, Cline과 Kilo Code는 비교 및 참고 대상이었으며, Jan.ai는 별도의 평가 대상으로 남겨 두었다.

이러한 구분은 도구 간 우열이 확정되었다는 의미가 아니다. 검증되지 않은 도구로 기존 환경을 성급하게 교체하지 않기 위한 운영 방식이다. 예를 들어 원격 추론 요청이 성공했다는 사실만으로 에이전트가 실제 코드 수정과 테스트까지 안정적으로 수행한다고 볼 수는 없다. 따라서 기본 도구를 즉시 교체하기보다, 후보별로 실제 작업 흐름을 검증한 뒤 변경 여부를 판단하는 편이 타당하다.

에이전트를 평가할 때는 설치 성공이나 모델 연결 여부만으로 충분하지 않다. 실제 개발 작업에서 요구사항에 맞는 변경을 수행하는지, 허용된 파일 범위를 지키는지, 관련 테스트를 실행하는지, 불필요한 변경을 만들지 않는지 확인해야 한다.

또한 오류 발생 시 복구 가능성, 기존 환경과의 호환성, 수동 수정에 필요한 시간도 중요하다.

비교의 신뢰도를 높이려면 동일한 기준 작업과 허용 파일 범위를 적용하고, 실행 명령과 출력, 테스트 결과 및 Git 변경 사항을 기록해야 한다. 도구마다 다른 조건으로 수행한 결과를 직접 비교하면 도구의 차이와 실험 조건의 차이를 구분하기 어렵기 때문이다.

현재 기록된 원격 추론 검증은 이러한 에이전트 비교를 완료했다는 의미가 아니다. 실제 코드 수정과 테스트를 포함한 작업 흐름, 그리고 후보 간 비교는 추가 검증이 필요한 영역이다.

## 6. 새로운 도구보다 검증 가능한 변경 절차를 우선하다

AI 도구는 빠르게 변화한다. 새로운 모델과 에이전트가 등장할 때마다 기존 환경을 교체하면 최신 기능을 접할 수 있지만, 호환성 문제와 설정 변경, 유지보수 부담도 늘어날 수 있다.

따라서 도구를 추가하기 전에 현재 환경의 구체적인 한계를 확인하고, 변경으로 얻을 수 있는 이점을 정의하는 것이 필요하다.

현재의 운영 원칙은 Windows 네이티브 환경과 Ollama, Aider를 기본 구성으로 유지하는 것이다. WSL2, 추가 RAG 구성, MCP 및 추가 에이전트는 실제 요구사항이나 검증 가능한 이점이 확인될 때 검토한다.

변경을 평가할 때는 가능한 경우 격리된 환경을 사용하고, 실행 명령과 결과, 테스트 및 변경 파일을 기록한다. 성공뿐 아니라 실패와 미검증 항목도 보존해야 이후의 판단에 활용할 수 있다.

이러한 접근은 특정 도구에 대한 선호보다 재현성과 변경 통제를 중시하는 개발 방식이다.

## 7. 다음 단계는 주장을 늘리는 것이 아니라 근거를 확보하는 것이다

이 글에서는 2026년 10월 15일에 수행한 로컬 추론 환경의 기본 연결 검증을 출발점으로, 당시 수립한 도구 선택 기준과 향후 평가 방향을 정리한다. 이후 수행한 후보 도구의 제한적인 연결 검증과 기본 RAG 테스트 결과는 각각 별도의 작업 기록으로 관리한다. 이러한 기록은 해당 테스트 범위의 결과를 보여 주지만, 도구의 전체 작업 흐름이나 일반적인 검색 성능을 입증하지는 않는다.

앞으로는 다음 사항을 검증할 계획이다.

1. Aider를 이용한 실제 코드 수정부터 테스트까지의 흐름을 확인한다.
2. 필요성이 확인된 대체 후보를 통제된 환경에서 평가한다.
3. 동일한 작업 조건에서 코드 품질, 테스트 결과, 파일 범위 준수 및 전체 작업 시간을 비교한다.
4. 과거 RAG 실험 결과는 기존 기록으로 보존하고, 개선 효과를 주장하기 전에는 재현 가능한 평가를 수행한다.
5. 실제 검증 결과와 운영상 필요성을 근거로 아키텍처 변경 여부를 결정한다.

이 항목들은 향후 계획이며, 현재 모두 완료되었다는 의미는 아니다.

## 맺음말

로컬 AI에서 하이브리드 AI까지 고민하면서 중요해진 것은 특정 도구를 선택하는 일보다 선택의 기준을 만드는 일이었다.

실제 개발 환경에서는 기능이나 홍보 자료만으로 결론을 내릴 수 없다. 환경을 구성하고, 실행 결과를 확인하고, 한계를 기록하며, 변경의 필요성을 근거로 판단해야 한다.

나에게 로컬 AI는 외부 서비스를 단순히 대체하는 수단이 아니다. 개발 환경을 직접 이해하고 통제하면서, 필요한 기술을 선택하고, 검증 결과를 축적해 더 나은 개발 흐름을 찾아가는 과정이다.

앞으로도 로컬 실행을 기본 출발점으로 삼되, 실제 요구사항이 있다면 다른 모델과 서비스를 함께 검토할 것이다. 중요한 것은 특정 도구를 고집하는 것이 아니라, 검증된 근거를 바탕으로 개발 환경을 지속적으로 개선하는 것이다.
